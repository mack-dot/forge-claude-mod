Forge rule: the person approves a short spec once; after that, code may change only if Dafny proves it still meets the spec. Use short sentences. Never write `.forge/approved.json`, never run `forge_check.py approve`, and never type `/forge approve yes` for the person: approval is their act. The checker is `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py"`.

A proof covers the proved function only. Code elsewhere that decides the same question itself (it reads the same field, or repeats the same comparison) goes AROUND the rule, and the proof says nothing about it. This conversation finds that code. Check the person named, if any: "$ARGUMENTS" (else every check in `.forge/forge.json`).

Do NOT change any application file in this conversation without the person's explicit word for that change.

1. READ the approved rule: run `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" spec` and read the spec and the decision record (`.forge/decisions/<check>.md`) of each check. Note what the rule decides on: the fields it reads (for example `body.for`, `householdId`), the comparison it makes (`spent + amount <= cap`), and the names of the functions that ask it (`mayRead`). Note any decision that limits WHERE a field counts (for example "body.for counts only on Companion's rows"): code that trusts that field elsewhere is the most likely bypass.
2. PROPOSE watched fields for each check without "watchedFields". They are a hard gate: once approved, `check` gives UNAPPROVED_BYPASS for every unallowed line that matches, so each term must be SPECIFIC. Use literal texts or regular expressions between slashes, in the forms that DECIDE:
   - a property access, with its dot: `.body.for` (not `body.for` or `for`);
   - a comparison or branch on the field: `/\bhouseholdId\s*(===|!==|==|!=)/` and `/(===|!==|==|!=)\s*[\w.]*\bhouseholdId\b/` (not the bare name `householdId`, which also matches every parameter, type and log line);
   - the rule's own comparison: `/spent\s*\+\s*amount[^;{]*<=?\s*cap/`.
   Never propose a bare common word (`cap`, `id`, `for`). Before showing them, PREVIEW each set: `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" bypass --count --rule <check> --set-terms '<term>' '<term>' …` (writes nothing). If a term matches more than about 30 lines, make it more specific and preview again. Show the person the terms, one line each with why, AND the measured count per term, then ask with AskUserQuestion: use these, change them, or skip. Only after a yes, write them: `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" bypass --rule <check> --set-terms '<term>' '<term>' …`.
3. SEARCH: run `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" bypass --json`. It searches the project's files (git's file list, else a walk without vendored and build folders, without documentation) outside the rule's own files (spec, implementation, answers, fuzz harness, emitted code, diff adapters and inputs) and outside places already reviewed. If there are many hits, group them by file and function first and say how many there are.
4. EXPLAIN each hit (or each group of hits in one function), in plain words, after reading the code around it: does this code decide the SAME question as the rule (who may read, whether the spend fits), a different question that only uses the same field, or is it a test or fixture? Name the input where it would answer differently from the proved rule, if you can see one (for example "a parent's own row with body.for set: the rule says no, this code says yes"). A hit in "a fuzzed file" may be the shipped function that the fuzz already compares with the rule; say so.
5. ASK the person per hit or group (AskUserQuestion, at most 4 questions per call, as many rounds as needed), with exactly these options:
   - "route it through the proved rule": propose the smallest change that makes this code call the proved rule (or its wrapper) instead of deciding itself. Show the change and apply it only after the person says yes to that change.
   - "it is fine (record why)": ask for the reason in one sentence (offer your own wording to confirm), then add it to the check's "allowedBypasses" by running `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" bypass --rule <check> --record <file>:<line> --note '<reason>'`. It records the line's SHA-256, so an edited line shows up again.
   - "make it part of a new rule": write down the question this code decides in one sentence and tell the person to start `/forge:add <that sentence>` next. Change nothing now.
6. END: run `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" bypass` again and show its first lines. Say plainly: this is a syntactic search, not a proof. In TS/JS and Python files only decision reads count (each hit names its kind, for example `comparison` or `filter-predicate`); other files, and files that do not parse (`FALLBACK to text search, not AST`), are a text search. It misses a value passed to another function or returned, dynamic access (`body[key]`), and code that decides the same question under other names. If you wrote "watchedFields" or a review, `.forge/forge.json` changed: tell the person to run `/forge approve`, then `/forge approve yes`. Never approve for them.
