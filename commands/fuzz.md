Forge rule: never write `.forge/approved.json` and never approve for the person. The checker is `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py"`.

The differential fuzz runs the person's real code and the compiled proved rule on the same inputs and reports every input where they disagree. Function the person named, if any: "$ARGUMENTS".

**If every check in `.forge/forge.json` that has code under test already has a "diff" entry:** run `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" diff --inputs 50000 --budget-ms 60000` (a deep run) and explain each disagreement in plain words (for `THROWS_ON_MESSY_INPUT`: the wrapper crashes on that field instead of failing closed): a bug in the code under test, or a place where the spec says something other than what the person meant. Change nothing without the person's word. Stop.

**Otherwise, set it up for the check:**
1. The check needs a "build" for the language of the code under test and a fresh build. If it has none, add it as `/forge:build-setup` describes (targets: py, js, go, java, cs, rs), then tell the person to run `/forge build` after approving.
2. Find the code under test: the shipped function that implements this rule today (keep it as it is) and the wrapper around the compiled proved code, if any. Ask if it is not clear. Never change the code under test to make it agree, and never modify any existing app file during set-up: only new files under diff/ and fuzz/, plus .forge/forge.json.
3. Write `diff/<check>_inputs.py` (Python, shared by every language): `def generate(rng)` returning one input as a plain JSON value; optional `def in_domain(input)` (False for inputs outside the spec's `requires`); and `decisions = [{'id': 'D1 …', 'input': …}, …]` copied from EVERY decision in `.forge/decisions/<check>.md` with the same concrete values. Cover zero, each limit and one past it, empty and duplicate values, and odd values (`rng.weird()`). Helpers: `rng.num(lo, hi)`, `rng.int`, `rng.pick`, `rng.string`, `rng.array`, `rng.bool`.
4. Write the evaluator for the code's language. Inputs and outputs are plain JSON with the same shape for the reference and every candidate.
   - JavaScript or TypeScript: `diff/<check>_diff.mjs` exporting `reference(input)` and `candidates = { name: input => output }`. Load the compiled proved code with `globalThis.forge.loadDafny('<relative path to the emitted .js>', ['ModuleName'])`; import TypeScript by its `.ts` path; convert integers with BigNumber (`globalThis.forge.require(process.env.NODE_PATH.split(':')[0] + '/bignumber.js')`). Entry: {"lang": "js", "inputs": …, "adapter": …}.
   - Python: `diff/<check>_diff.py` with `reference(input)` and `candidates = {name: function}`. Entry: {"lang": "py", "inputs": …, "adapter": …}.
   - Go: `diff/<check>_diff.go`, starting with `//go:build forge` and `package main`, defining `func reference(in Input) any` and `var candidates = map[string]func(Input) any{…}`. Import the proved code by its Dafny module name (for example `m_Wallet "Wallet"`, call `m_Wallet.Companion_Default___.Method(...)`) and the code under test by its module path. Helpers: `forgeDafnyInt(v)`, `forgeInt(v)` (*big.Int), `forgeInt64(v)`. Entry: {"lang": "go", "inputs": …, "adapter": …}. Forge builds it in `.forge/cache/` (needs go and goimports); the check's build targets must include "go".
   - Rust: `diff/<check>_diff.rs` defining `pub fn reference(i: &Value) -> Value` and `pub fn candidates() -> Vec<(&'static str, fn(&Value) -> Value)>`, using `crate::forge::{self, json, Value}` and `crate::proved::<Module>`; include the code under test with `#[path = "<relative path>"] mod name;` or a crate dependency in the entry's "rust_deps" ({"crate": "{ path = \"…\" }"}). Helpers: `forge::int`, `forge::out`, `forge::i64`, `forge::u64`. Entry: {"lang": "rs", "inputs": …, "adapter": …}. Forge builds it with cargo in `.forge/cache/`; the build targets must include "rs".
   - Java: `diff/<check>_diff.java` with `public class ForgeAdapter` (default package) defining `public static Object reference(Map<String, Object> in)` and `public static Map<String, Function<Map<String, Object>, Object>> candidates()`. Dafny integers are `java.math.BigInteger`; helpers `ForgeMain.big(v)`, `ForgeMain.lng(v)`. List the code under test in the entry's "java_sources" (files or folders). Entry: {"lang": "java", "inputs": …, "adapter": …, "java_sources": [...]}. The build targets must include "java".
   - C#: `diff/<check>_diff.cs` with `public static class ForgeAdapter` (global namespace) defining `public static object Reference(Dictionary<string, object> input)` and `public static Dictionary<string, Func<Dictionary<string, object>, object>> Candidates()`. Dafny integers are `BigInteger`; helpers `ForgeMain.Big(v)`, `ForgeMain.Lng(v)`. List the code under test in "cs_sources". Entry: {"lang": "cs", …}. Needs the .NET SDK; the build targets must include "cs".
   - Add `.forge/cache/` to the project's `.gitignore`.
   - Any other language (Swift, Kotlin, Ruby, …): a small program in that language that prints `{"candidates": ["name", …]}` as its first line, then for each line `{"input": …}` on standard input prints one line `{"reference": …, "candidates": {"name": …}}`, calling the compiled proved code and the code under test; an exception becomes `{"__throws__": "<ErrorName>"}`. Entry: {"lang": "cmd", "inputs": …, "run": ["<program>", "<args>"]}. Say plainly that this evaluator is new code.
   - **The wrapper, with messy inputs (every language):** if there is a wrapper that turns app or JSON values into the proved code's values, also define in the adapter a `wrapper` (or several `wrappers`) that calls the REAL wrapper with the RAW input (no conversion in the adapter), and a fail-closed function returning the spec's fail-closed answer for a value the proved rule does not take (for example `{ effect: "forbid", rule: "other_group" }` when a group id is not text), or the language's "no value" when the proved rule takes the input. Per language: JavaScript/TypeScript `export const wrappers = { name: fn }` (or `export function wrapper(input)`) and `failClosed(input)` → `undefined`; Python `wrappers = {name: fn}` (or `def wrapper(inp)`) and `fail_closed(inp)` → `None`; Go `var wrappers = map[string]func(json.RawMessage) any{…}` (or `func wrapper(raw json.RawMessage) any`) and `func failClosed(raw json.RawMessage) any` → `nil`; Rust `pub fn wrappers() -> Vec<(&'static str, fn(&Value) -> Value)>` (or `pub fn wrapper(raw: &Value) -> Value`) and `pub fn fail_closed(raw: &Value) -> Option<Value>` → `None`; Java `public static Map<String, Function<Object, Object>> wrappers()` (or `public static Object wrapper(Object raw)`; the raw value is Map / List / String / Boolean / BigInteger / BigDecimal / null) and `public static Object failClosed(Object raw)` → `null`; C# `public static Dictionary<string, Func<JsonElement, object>> Wrappers()` (or `public static object Wrapper(JsonElement raw)`) and `public static object FailClosed(JsonElement raw)` → `null`. All are optional; an adapter without them still builds. Wrappers are also called with the plain inputs. Ask the person which fail-closed answer the spec means if it is not written down. Forge then sends each field as undefined (JavaScript only), null, a number, a boolean, "", a lone surrogate, a long text, [], {}, the number as text, or removed; a throw or panic is reported as `THROWS_ON_MESSY_INPUT`. Rust does not get the lone surrogate: serde_json rejects it while it parses, before any wrapper runs (the result lists it under `skipped_kinds`); say so. Messy is on by default for such adapters; never set `"messy": false` to hide a finding. Fields the app never gets from outside (computed booleans, database-checked enums) may go in `messy_skip = ['field', 'list[].field']` in the inputs module; say which and why.
5. Add the entry to the check's "diff" (a list if there are several languages), with "watch": [files of the code under test]. Edits to those files trigger a run at the end of each Claude turn (about a second).
6. Run `python3 "${CLAUDE_PLUGIN_ROOT}/cli/forge_check.py" diff` once and explain each disagreement as above.
7. Tell the person, as the one next step: "Type `/forge` to read the change and approve it (`/forge approve yes`); Forge then builds and runs this test by itself."
